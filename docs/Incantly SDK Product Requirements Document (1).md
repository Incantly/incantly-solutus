# Incantly SDK: Product Requirements Document

Draft v1 · October 2026 · Owner: Iteoluwakisi

## 1. Summary

Incantly turns the concept a learner is studying into a live, interactive visualization inside their notes. The visualization is generated by an AI agent. To make that fast, reliable and consistent, the agent must not write infrastructure. It should pick ready-made building blocks from the SDK (graphs, 3D space, physics, controls, formulas, zoom, timing) and only write the content that is specific to the concept.

The whole SDK is plain HTML, CSS and JavaScript, bundled in the app. The agent returns three short fragments (HTML, CSS, JS) that are dropped into a bundled shell and run in a sandboxed iframe inside a TipTap node.

## 2. Problem

- A DSL for visualizations is a closed language the model has never seen, and every new kind of figure needs compiler work.
- Free-form HTML from a model is inconsistent: different controls, different themes, broken zoom, unsafe code, slow on iPad.
- Cloning a single tool such as Desmos limits the product to graphing, while Incantly must cover physics, chemistry, biology, maths and more.

## 3. Goals and non-goals

### Goals

1. The agent writes only scene content. Every reusable capability ships in the SDK.
2. A first generation works without repair at least 85 percent of the time.
3. Every figure has the same controls, theme and behaviour, so users learn them once.
4. Users can tweak formulas, parameters, timing and view, and the tweaks are saved with the note.
5. Runs on web and iPad with the same code. Safe to run untrusted generated code.
6. No third-party 3D engine in v1.

### Non-goals (v1)

- Photorealistic 3D, real lighting, textured meshes.
- A visual editor for building figures by hand.
- Server-side execution of generated code.
- Multi-user live collaboration inside a figure.

## 4. Users

- **Learner:** reads a note, taps a concept, sees it come alive, tweaks it to understand it.
- **The agent:** reads the SDK rules, picks components, writes the scene fragments.
- **Developer (Incantly team):** adds components and kits, tunes rules, watches failure rates.

## 5. Architecture

Three layers, three owners.

| Layer | Owner | Lives |
| --- | --- | --- |
| Shell: html, head, body, theme CSS, slots | Incantly | Bundled in the app |
| Engine and component library | Incantly | Bundled in the app |
| Scene: HTML, CSS, JS fragments | The agent | Generated per request, saved in the note |

```html
<!doctype html>
<html>
<head>
  <style>/* base theme + controls CSS */</style>
  <style>/*__AGENT_CSS__*/</style>
</head>
<body>
  <div id='controls'></div>   <!-- engine builds this -->
  <div id='stage'>
    <!--__AGENT_HTML__-->
  </div>
  <script>/* engine.js bundled here */</script>
  <script>/*__AGENT_JS__*/</script>
</body>
</html>
```

The app fills the three slots and loads the result as the srcdoc of an iframe with sandbox='allow-scripts', no network access and a strict content security policy. The agent's rules and prompts stay on the server and never ship to the browser.

### Request flow

1. User selects text or a concept in a note.
2. Backend sends rules plus the concept to the model.
3. Model returns HTML, CSS and JS fragments.
4. Backend validates them and returns them to the app.
5. A TipTap node stores the fragments and renders the iframe.
6. The engine builds the controls; the user tweaks; tweaks are saved to the node.

## 8. Safety and validation

- Iframe sandbox with allow-scripts only, no same-origin access, no network, strict content security policy.
- Backend validator on every generation: size limits, no network calls, no eval or Function, no parent or top access, no external scripts or images, no hard-coded colours.
- Runtime limits: frame time budget, shape budget, expression complexity cap, loop guard.
- Formulas always go through the safe parser.
- Prompts, rules and generation pipeline stay on the server. The engine is minified with source maps off in production.

## 9. The agent contract

The agent receives rules.md as its system prompt. The rules state:

1. Only write the three fragments. Never write html, head, body or controls.
2. Pick components from the catalog first; write raw HTML, SVG or canvas only for what no component covers.
3. Declare every adjustable quantity with inc.param or a formula so the user can tweak it.
4. Use theme tokens only.
5. Stay within the budgets for shapes, points and frame work.
6. Prefer a few well-chosen controls over many.

### Example: a sine wave

```html
<!-- AGENT_HTML -->
<div id='g'></div>
```

```js
// AGENT_JS
const A = inc.param('amplitude', {min: 0.5, max: 4, value: 2});
const w = inc.param('frequency', {min: 0.5, max: 6, value: 2});
const phi = inc.param('phase', {min: 0, max: 6.28, value: 0});
inc.timing({duration: 2, loop: 'loop'});

const g = inc.graph2d('#g', {x: [-6.28, 6.28], y: [-5, 5]});
const y = inc.formula('A*sin(w*x + phi + t)', {vars: {A, w, phi}});
g.plot(y, {color: 'a', animate: true});
```

### Example: projectile

```js
const v = inc.param('speed', {min: 5, max: 40, value: 22, unit: 'm/s'});
const a = inc.param('angle', {min: 5, max: 85, value: 45, unit: 'deg'});
const g = inc.param('gravity', {min: 1, max: 25, value: 9.8, unit: 'm/s2'});

const world = inc.physics2d('#stage', {gravity: g});
const ball = world.circle({x: 0, y: 0, r: 0.4, vx: () => v.value*Math.cos(a.rad), vy: () => v.value*Math.sin(a.rad)});
world.trail(ball, {every: 0.5});
world.showVectors(ball, {components: true});
inc.readout({range: () => world.range(ball), peak: () => world.peak(ball)});
```

In both examples the agent writes no loop, no slider, no zoom, no theme and no event code.

## 10. Non-functional requirements

| Area | Target |
| --- | --- |
| Time to first render | Under 1 second after the scene arrives on a mid-range iPad |
| Frame rate | 60 fps for typical figures, never below 30 on the oldest supported iPad |
| Engine size | Under 250 KB minified and compressed for the core; kits load on demand |
| Memory | Under 120 MB per live figure; off-screen figures destroyed after 20 seconds |
| Accessibility | Keyboard operable, text description for every figure, reduced-motion respected, contrast meets AA |
| Offline | Engine and saved figures work without a network connection |
| Determinism | Same scene and values give the same result on every device |

## 11. Success metrics

- First-attempt success rate (renders without error): 85 percent or higher.
- Success after one repair retry: 97 percent or higher.
- Median generated code size: under 80 lines.
- Median time from request to rendered figure: under 8 seconds.
- Share of figures where the user changes a parameter: 60 percent or higher.
- Figures abandoned or deleted within a minute: under 10 percent.

## 13. Risks and open questions

| Risk | Mitigation |
| --- | --- |
| The model misuses or invents SDK functions | Short, typed API listing in the rules; validator rejects unknown calls; worked examples |
| Fake 3D looks flat for some topics | Asset library and an optional WebGL backend later, behind the same interface |
| Large catalog lowers first-attempt success | Component picker step: the model first names the components it will use, then writes the scene |
| iPad memory pressure | Snapshot and destroy, live-figure cap, resolution budgets |
| Users edit a formula into something invalid | Inline errors, one-tap reset to the agent's original |
| Rules leak through the browser | Rules and prompts stay on the server |

### Open questions

1. Which expression library: math.js or a smaller custom parser?
2. How are domain kits delivered: one bundle or lazy modules per subject?
3. Should figures in one note share state (change a value in one, update another)?
4. Is the asset library curated by hand or generated and reviewed?
5. What is the edit-by-prompt flow: patch the fragments or regenerate and merge tweaks?

## 14. Decisions already made

- HTML, CSS and JavaScript, with SVG as the primary rendering layer and canvas for dense animation (section 22). No Three.js in v1.
- No DSL and no Desmos clone.
- The app bundles the shell and engine; the agent fills three slots.
- The agent declares parameters and the engine builds the controls.
- Generated code always runs in a sandboxed iframe inside a TipTap node.
- Agent rules and prompts stay on the server.

## 15. Reference study: Anatomy

**Source note.** This section is based on the Anatomy README and its full SKILL.md (read through the Hermes copy of the skill), including the description of every kit file. The kit source files themselves were not read, because GitHub blocked automated access to the kit folder. Before the engine is built, an engineer should read these files directly: iso-kit.mjs (camera, solids, painter's order), lathe.mjs, tube.mjs, audit.mjs and the references folder. Anatomy is MIT licensed, so ideas and code can be reused as long as the license notice is kept.

### 15.1 What Anatomy is

Anatomy is an agent skill: a folder holding a SKILL.md (the workflow and craft rules), a kit (the drawing library), references (long guides the agent opens only when needed), scripts (headless-browser checks), examples and evals. Given a concept, the agent invents a physical machine whose working is the concept, builds it from 40 to 150 small shaded isometric parts in SVG (with optional WebGL shaders and an optional 3D mode), frames it in a card with a live readout, makes it respond to pointer and keyboard, and then checks its own work with geometry audits and close-up screenshots.

It runs inside a developer agent (Claude Code, OpenCode, Codex) with Node and headless Chrome. Its own sizing step says a Figure takes 30 to 90 minutes, a Hero 2 to 4 hours and an Epic 6 hours or more.

### 15.2 Why we cannot use it as it is

| Question | Anatomy | Incantly |
| --- | --- | --- |
| What it shows | An invented machine that stands for the idea | The real phenomenon: the projectile, the magnet, the wave |
| Time to result | 30 minutes to several hours | Under 10 seconds |
| Who writes the geometry | The agent, part by part, using the kit | The engine; the agent picks and configures components |
| Where it runs | A developer machine: Node build, headless Chrome | The learner's device: web and iPad |
| Output | A finished HTML page, SVG or React component | Fragments of real HTML, CSS and JavaScript saved inside a note |
| Graphs and data | Not a chart library | Graphs, formulas and sliders are core |
| User control | Hover, drag, keyboard | Also editable formulas, timing and parameters |
| Trust | The developer reviews the output | Generated content is untrusted and must be contained |

| ID | Idea in Anatomy | How Incantly uses it |

### 15.4 What we deliberately do not borrow

- **The invented-machine metaphor.** A cache is not a lock in our product. A learner studying a magnet needs a magnet.
- **Very high detail.** 40 to 150 parts, screws and knurls take hours. We show the few parts that carry the concept, drawn cleanly.
- **The build step.** Anatomy compiles a page with Node. Our engine is already bundled, so there is nothing to compile at generation time.
- **Long self-review loops.** Close-up screenshots of every joint cost minutes. Our checks are automatic and take under a second.
- **The 3D mode.** It is beta and slow on phones in its own tests. We keep 3D to depth-sorted SVG and canvas in v1.

## 17. Borrowed mechanisms in detail

Everything below is written so a human or an agent can implement it without reading Anatomy. API names are proposals; keep the behaviour.

### 17.1 Plan before code (BR-2)

The agent's first reply is a plan. It is small, and the backend can reject a bad plan in milliseconds, before the expensive second call.

```js
{
  concept: 'projectile motion',
  idea: 'Horizontal speed stays constant; vertical speed changes with gravity.',
  size: 'standard',
  components: ['physics2d', 'graph2d', 'readout', 'controls'],
  model: { inputs: ['speed', 'angle', 'gravity', 'height'],
           outputs: ['range', 'peak', 'flightTime'] },
  parts: ['ground', 'launch tower', 'ball', 'path', 'time-step dots',
          'horizontal-speed arrow', 'vertical-speed arrow'],
  moves: 'The ball follows the model; both arrows update every frame.',
  controls: ['speed', 'angle', 'gravity', 'height']
}
```

The backend rejects the plan when any of these is true:

- A component is not in the catalog.
- The part count or control count is over the size budget.
- An output is listed that no input can affect.
- The idea field is empty or longer than 200 characters.

Why it matters: the idea sentence forces the agent to decide what the figure is meant to teach. Anatomy asks for the same thing ('say in one sentence what moves and what that motion means').

The plan is a plain-language note for the validator. It is not a language, it is never rendered, and the engine never reads it. The scene itself is always real HTML, CSS and JavaScript.

### 17.2 The one-model rule (BR-3)

Every number the learner sees, in the readout, a label or a caption, must come from the same model that moves the parts. If a number is typed into text, it will be wrong the moment a slider moves.

Correct:

```js
const m = inc.model(({ speed, angle, gravity, height }) => {
  const a = angle * Math.PI / 180;
  const vx = speed * Math.cos(a), vy = speed * Math.sin(a);
  const T = (vy + Math.sqrt(vy * vy + 2 * gravity * height)) / gravity;
  return { vx, vy, T, range: vx * T, peak: height + vy * vy / (2 * gravity),
           x: t => vx * t, y: t => height + vy * t - 0.5 * gravity * t * t };
});

inc.onFrame(t => ball.at(m.x(t), m.y(t)));
inc.readout({ Range: () => m.range, Peak: () => m.peak, Time: () => m.T });
```

Wrong (the validator flags literal numbers followed by a unit inside strings that are passed to a label or readout):

```js
inc.caption('The ball travels 48.4 m and peaks at 12.3 m.');
```

### 17.3 Geometry once, painter's order, wrap (BR-4, BR-5)

- Build every static shape once, outside onFrame. Move it with a transform (`part.at(x, y)`, `part.rotate(a)`). Rebuild a shape per frame only when its outline changes (a stretching spring, a growing wave).
- Draw in painter's order: farther things first, nearer things on top. The agent never sorts by hand; it adds parts and the engine sorts them by depth every frame.
- Anything that wraps another part is split into a back half and a front half, so the wrapped part appears to pass through it. The engine does this with one call.

```js
const scene = inc.space3d('#stage', { view: 'iso' });
const rod    = scene.cylinder({ axis: 'x', r: 0.3, len: 6, tone: 'mid' });
const spring = scene.coil({ axis: 'x', r: 0.8, turns: 8, len: 5 });
scene.wrap(rod, spring);   // spring is split: back half behind the rod, front half over it
```

For flat pairs, the same idea applies to a ring around a cylinder or a magnet field loop around a bar: call `scene.wrap(inner, outer)`.

### 17.4 Tones and colour (BR-6)

Parts are filled with solid tone colours, so nearer parts hide farther ones. No see-through outlines and no dashed hidden lines.

| Token | Used for |
| --- | --- |
| lo | Base plates, floors, feet |
| mid | Structure: posts, rails, frames |
| hi | The subject of the figure |
| lit | Exactly one accent per figure: the part the learner should watch |
| faint | Grooves, grid lines, minor ticks |
| a, b, c | Data colours: only when colour carries meaning (red and blue magnet poles, three vector components) |

Rules: one lit part per figure; colour only when colour is the subject; faces are shaded by facing direction (the engine's shade function gives four side tones and a lighter top). Agent CSS may use tokens only.

### 17.5 The card (BR-7)

Every figure is wrapped by the shell in the same card, built from plan fields:

- Top left: figure number inside the note (Fig 1, Fig 2).
- Top right: a short title.
- Bottom left: one-line hint ('Drag the sliders. Tap a part to learn more.').
- Bottom right: the live readout.
- Under the card: legend keys and one true caption.

Words stay out of the drawing apart from short part labels. The agent only supplies `card: { title, hint }`.

### 17.6 Motion (BR-8)

```js
x = inc.follow(x, target, { rate: 8 });   // exponential: x += (target - x) * (1 - exp(-rate * dt))
s = inc.spring(s, target, { k: 120, damping: 14 });
inc.idle({ after: 4, sweep: 'angle' });   // gently sweeps a parameter when nobody touches the figure
```

Rules:

- Motion is time-based, never frame-based, so it looks the same at 30 and 120 fps.
- The idle tour loops, and stops the moment the learner touches anything.
- The loop stops when the figure is off-screen or the tab is hidden.
- Reduced motion gives one still frame and no idle tour.
- Write to element attributes directly; do not rebuild markup every frame.

### 17.7 Checks that replace the long review loop (BR-9)

Anatomy verifies with audits and close-up screenshots. We keep the idea and make it fast.

**In-app check, runs on every generation in a hidden frame, under 1 second:**

| Check | Pass condition |
| --- | --- |
| Runs | 60 frames with no thrown error |
| Numbers | No NaN or Infinity in the model outputs |
| Sweep | Every parameter set to its minimum, middle and maximum, while playing and while paused, with no error and with the drawing responding each time |
| Frame cost | Average frame under 8 ms on the test device |
| Budget | Shape count and point count under the size budget |
| Bounds | Everything drawn at default values is inside the stage |
| Parts | Every part named in the plan exists |
| Tokens | No hard-coded colours; no literal numbers in labels |

**Offline check in CI (seconds to minutes, never blocking a learner):**

- Screenshots at three widths in light and dark, compared to golden images.
- A depth-order audit for space3d scenes: where two parts overlap on screen, the nearer one must be drawn on top.
- A line-end check for diagrams: every drawn line ends on a shape, another line or a marked terminal dot.
- Eval runs (17.8) that report first-attempt success rate.

When a check fails, the message goes to the agent for one repair attempt. Make it specific enough to fix:

```
CHECK FAILED sweep: with gravity=1 and speed=40 the scene threw
'Cannot read properties of undefined (reading x)' at AGENT_JS line 14.
Fix it and return all three fragments.
```

The examples folder holds finished, reviewed scenes: the three figures already built (projectile, buoyancy, magnets), rewritten against the kit, then more. The agent receives the closest example with every request.

## 18. How the agent's code runs (no DSL)

**Decision.** There is no DSL and no scene-description format. The agent writes real HTML, CSS and JavaScript, as in Anatomy. An earlier draft of this section proposed a data format (formulas and parts listed as data). In practice that was a DSL, and it has been removed.

### 18.1 Does Anatomy use a DSL?

No. This is what the README and SKILL.md show:

- The agent writes ordinary JavaScript: a Node build script that imports the kit and calls normal functions (slabOf, cylinder, extrude, planOutline, topTicks, knurl, coil, lathe, tubePieces), then assembles the page with solidSvg, lineSvg, figureSvg, plateHtml and pageHtml. For live motion it writes plain browser JavaScript, or React components in TypeScript.
- The kit is a library: functions with documented signatures (references/kit.md). There is no custom syntax and no interpreter.
- SKILL.md is instructions for the agent, written in English. It is not a language either.
- Its geometry modules and its small model (rig.ts in the test-rig example) are plain code.

Anatomy is the pattern we follow: a well-documented library, short rules, worked examples, and an agent that writes real code against them.

### 18.2 What this means for us

| Part | What it is |
| --- | --- |
| Kit API | Normal JavaScript functions (inc.param, inc.onFrame, inc.graph2d, inc.space3d and so on) documented in the references |
| Agent output | Three fragments: HTML, CSS and JavaScript. Nothing else. |
| Formulas | A maths expression string passed to inc.formula and evaluated by math.js. It is ordinary maths, the same thing a learner types into a calculator, and the learner can edit it |
| Plan (17.1) | A plain-language note checked by the validator. Never executed, never rendered, never read by the engine |
| Stored in the note | The three fragments and the learner's changed values |

### 18.3 Keeping the benefits of a structured format without one

| Benefit | How we get it with real code |
| --- | --- |
| Short output | The kit does the work, so a scene is 30 to 80 lines |
| Validation | A static scan of the code: only allowed inc calls, no network, no eval, no hard-coded colours, size caps |
| Easy edits | Scenes are short, so edit-by-prompt regenerates the changed fragment or applies a small code diff |
| Safe to run | Always sandboxed (18.4) |
| Fast checks | The in-app check suite in 17.7 |

### 18.4 Running the code safely

Agent code is untrusted, so it always runs in a sandboxed iframe: sandbox='allow-scripts' only, no same-origin access, no network, a strict content security policy, srcdoc delivery and a postMessage bridge to the host. Compute-only work may run in a Web Worker. The shell and engine are bundled in the app, so the iframe loads them without a network request.

The cost to manage is that every iframe boots its own copy of the engine. Mount an iframe only when its block is near the viewport (HO-4), show a snapshot otherwise, cap live figures (HO-6), load kit modules (3D, physics, KaTeX) only when the scene uses them, and measure boot time per figure on the oldest supported iPad against the first-render budget in 16.1.

### 18.5 About hiding how it is built

- Nothing that runs in a browser can be fully hidden. The iframe, its DOM and its code are visible to a curious person.
- What can be protected: the prompts, rules, planner, validator and generation pipeline (server); the example library and eval data (server); and the engine code (minified, source maps off in production).
- What cannot: the scene's own code. It is the learner's content, stored in their note.
- iPad app: leave web inspection off in release builds.
- The real advantage is the quality of the kit, the rules, the examples and the evals, not secrecy about how figures are drawn.

### 18.6 Hiding generation inside the TipTap node

Section 18.5 sets the principle: nothing in a browser is fully hidden, so the aim is to shrink the surface. The host tries the following in release builds, so that opening devtools on a note shows a running figure, not a transcript of how it was made.

| Leak | What the host does |
| --- | --- |
| Node attributes | The node stores only the three fragments, the learner's changed values and the snapshot (HO-1). The prompt, rules, plan, model name, agent conversation, check reports and repair history never reach the client: generation and repair run server-side, and only fragments that passed the probe cross the bridge |
| Bridge messages | Traffic stays within the message list in HO-3. No postMessage payload carries generation data or debugging scaffolding |
| Console output | The engine and inc-bridge make no console calls in release; the build strips any that remain (18.5). The error boundary (RT-7) catches agent-thrown exceptions and reports them over the bridge, so a running figure leaves no uncaught errors in the console |
| Web inspection | On iPad, web inspection is off in release builds. On web nothing is suppressed, and no anti-devtools tricks are added: debugger loops and blocked context menus are hostile to legitimate users and do not stop a determined reader |
| Network tab | The iframe makes no requests (no network, strict CSP; 18.4), and its engine arrives pre-warmed (25.4), so there is no generation traffic to observe while a figure runs |

What remains visible is the scene's own code, which is the learner's content (18.5). That is accepted. The goal is a console clean of generation internals, not an impossible wall.

## 21. Engine rules learned from the bicycle build

The bicycle chain figure was generated with the shell, engine and fragments pattern from section 18. It worked, and it showed one bug and several patterns that must become rules before the SDK is built.

### 21.1 The paused-slider bug

**Symptom.** With the figure paused, moving a slider changed the number beside it but not the drawing. The drawing only updated while the animation was playing.

**Cause.** The engine called the agent's frame function only from the animation loop, and only while playing. A slider input only changed the parameter value; nothing asked for a redraw.

**Rule: a parameter change always redraws, whether the figure is playing or paused.** Paused means time stops, not that the figure stops responding.

How the engine does it:

- The engine keeps a dirty flag. Every parameter change, restart, step, zoom, resize and theme change sets it.
- The loop draws when the figure is playing or dirty. When paused, it calls the agent's frame function with dt = 0, so nothing advances in time but the drawing is recomputed from the new values.
- When the figure is paused and not dirty, the loop does no drawing work at all.

```js
let dirty = true;
const redraw = () => { dirty = true; };

slider.addEventListener('input', () => { p.value = +slider.value; redraw(); notifyHost(); });

function loop(now) {
  const dt = Math.min((now - last) / 1000, 0.05) * speed; last = now;
  if (playing && !hold)      { t += dt; frame(t, dt); dirty = false; }
  else if (dirty && !hold)   { frame(t, 0);            dirty = false; }
  updateReadouts();
  requestAnimationFrame(loop);
}
```

What the agent must do: its frame function must be safe to call with dt = 0, and must draw only from the current parameter values and its own state.

```js
// Wrong: advances on every call, so a paused redraw would move the figure
ang += 0.05;

// Right: advances by time, so dt = 0 changes nothing but the drawing still updates
ang += rpm.value * TAU / 60 * dt;
```

**Check.** The in-app sweep (17.7) now runs each parameter at minimum, middle and maximum while paused, and fails if the drawing does not change. Section 20.2 step 1 also requires this to pass.

### 21.2 Event handling rules

Every listener is written once, by the engine. The agent never writes one.

1. **Delegation.** One listener per event kind on the controls container, not one per control. Controls are found by data attributes.
2. **Pointer events** (pointerdown, pointermove, pointerup with pointer capture) for dragging, panning and pinching, so mouse, touch and pen share one code path. Where a figure must not block page scroll, set touch-action to pan-y until the learner taps it.
3. **Passive listeners** for wheel and touch unless the handler must call preventDefault (zoom). Non-passive listeners are the exception and are listed in the engine.
4. **No drawing inside an event handler.** A handler updates a value and sets the dirty flag. The next animation frame draws, at most once per frame, however fast the slider moves.
5. **One animation loop** for the whole figure. The agent uses inc.onFrame and never calls requestAnimationFrame, setInterval or setTimeout.
6. **Throttle messages to the host.** Send valueChanged at most once every 100 ms (trailing edge), so dragging a slider does not flood the bridge.
7. **Clean up.** Every listener and observer is registered with one AbortController, so destroying a figure removes all of them.
8. **Verify message sources.** Accept messages only when the source is the expected window.

```js
controls.addEventListener('input', e => {
  const el = e.target.closest('[data-param]');
  if (!el) return;
  params[el.dataset.param].set(+el.value);     // sets the value, marks dirty, queues the host message
}, { signal });

controls.addEventListener('click', e => {
  const b = e.target.closest('[data-action]');
  if (!b) return;
  actions[b.dataset.action]();                 // play, restart, step, reset, zoom, ...
}, { signal });
```

### 21.3 Frame cost rules

- No layout reads inside the frame function (getBoundingClientRect, offsetWidth, scrollHeight). Measure in a ResizeObserver and cache.
- Write an attribute or style only when its value changed.
- Rebuild geometry only when the parameters that shape it change. The bicycle figure rebuilds sprocket teeth and chain length only when a teeth slider moves (a keyed rebuild), then just updates transforms and dash offsets each frame.
- Build static shapes once; move them with transforms.
- Update readouts only when their text changed.
- Do not use innerHTML inside the frame function.

### 21.4 The reusable control library

All controls come from one factory in the engine, so they share markup, classes, theme tokens, keyboard behaviour and touch size. The agent declares a control; the engine builds it.

| Group | Control | Declared by the agent as | Notes |
| --- | --- | --- | --- |
| Transport | Play and pause | Built in, always present | One button; label and aria-pressed change with state |
| Transport | Restart | Built in | Resets time and calls the agent's reset callbacks |
| Transport | Speed | Built in; default set with inc.timing | Options such as 0.1x, 0.25x, 0.5x, 1x, 2x |
| Transport | Step back and forward | inc.steps(\[...\]) | Shown only when steps exist, with a progress label |
| Parameter | Slider with number field and unit | inc.param(name, options) | Arrow keys change by one step, Shift by ten |
| Parameter | Switch | inc.toggle(name, options) | Boolean value |
| Parameter | Segmented control or dropdown | inc.choice(name, options) | Segmented up to four options, dropdown above that |
| Parameter | Action button | inc.button(label, fn) | The agent passes a function; the engine attaches it through delegation |
| Parameter | Colour | inc.color(name, options) | Theme tokens only |
| View | Zoom in, zoom out, reset view | Built in for graph and space components | Pinch and wheel also work |

## 22. SVG: the primary rendering layer

SVG is the default way figures are drawn in Incantly. The bicycle figure is made of SVG (sprockets, chain, crank), Anatomy's isometric parts are SVG, and every graph, diagram and 3D-looking scene in v1 is SVG unless it has too many moving elements, in which case it moves to canvas. Earlier sections mentioned SVG in passing. This section makes it a first-class part of the SDK, with its own module (inc-svg), rules and requirements.

### 22.1 Choosing a layer

| Layer | Use for | Avoid for |
| --- | --- | --- |
| SVG (default) | Graphs, diagrams, mechanisms, depth-sorted 3D-looking parts, labels, anything the learner taps, highlights or zooms. Up to about 600 elements | Thousands of moving elements |
| Canvas 2D | Particles, fluids, dense vector fields, thousands of points, motion trails | Anything the learner must tap, label or highlight individually |
| HTML and CSS | Text, controls, readouts, tables, captions; CSS 3D for one simple spinning solid | Drawings with many parts |
| WebGL | Not in v1 |  |

A figure may mix layers: an SVG stage with a canvas layer behind it for particles, sharing one coordinate system (SV-13).

### 22.2 Why SVG first

- It stays sharp at any zoom and on retina iPads.
- Every shape is an element, so tapping, hovering, focusing, labelling and highlighting need no hit-testing code.
- It is styled by the theme tokens, so light and dark mode work without extra code.
- Depth sorting is element order, which suits the painter's-order approach in 17.3.
- The same drawing exports as a vector file and makes the snapshots used for off-screen placeholders.
- Models write SVG well.

### 22.3 The inc-svg module (what the agent never writes)

| Feature | What it does |
| --- | --- |
| inc.svg(el, {viewBox, title, desc}) | Creates the stage: responsive viewBox, role and accessible name |
| Layers | svg.layer('back'), 'mid' and 'front' are ordered groups; parts are added to a layer and the engine keeps the order |
| Element builders | svg.path, line, circle, rect, polygon, text, group. Each returns a handle with set(attrs), at(x, y), rotate(deg, cx, cy), scale, show and hide. A handle writes an attribute only when the value changed |
| Path helpers | line(points), curve(fn, x0, x1, steps), arc(cx, cy, r, a0, a1), hull(circles) for belts and chains, gear(teeth, radius) for sprockets, arrow(from, to) |
| Tones | .tone('lo' or 'mid' or 'hi' or 'lit') applies fill and stroke from tokens; shading gradients are created once per figure |
| Symbols | svg.symbol(name, shape) and svg.use(name, x, y) for repeated teeth, links and ticks |
| Parts | svg.part(name, element, {label, info}) registers a part for highlight, dimming, callouts and keyboard focus |
| Coordinates | svg.toLocal(clientX, clientY) maps a pointer position to figure coordinates with a cached matrix |
| View | Zoom and pan by changing the viewBox, with non-scaling strokes and a reset |
| Flow | path.flow({link}) and path.flowTo(distance) move dashes along a path, for chains, belts, currents and streams |
| 3D output | inc.space3d draws into the same stage, as depth-sorted SVG paths |
| Export | svg.toString() with tokens resolved, svg.toPng() for snapshots |

### 22.4 Rules for SVG written by the agent

1. Always use a viewBox. Never set fixed pixel width or height. The figure scales to its container.
2. Never hard-code colours. Use classes or tone tokens such as var(--a).
3. Do not write IDs for gradients, clip paths or markers. The engine creates them and prefixes every generated ID with the figure ID, so two figures never collide, including when SVG is exported or inlined into another page.
4. Build once, move with transforms. Rebuild a path's d attribute per frame only when its outline changes. In the bicycle figure the sprocket outline is rebuilt only when a teeth slider moves; each frame only changes a rotate transform and a dash offset.
5. Use symbols and use for repeated shapes.
6. Stay under about 600 elements. Above that, use canvas.
7. Avoid filters, blur, masks and large shadows. They are slow on iPad. Fake depth with tones and gradients.
8. Use non-scaling strokes for lines that must keep their thickness when zoomed.
9. Text inside the SVG is short labels only, at least 12 px at 100 percent. Long text belongs in HTML.
10. Every figure has a title and a description. Interactive parts are focusable and have accessible names.

### 22.5 Example: the bicycle chain with the kit (target API)

The published prototype wrote these SVG calls by hand. With inc-svg the same figure becomes:

```js
const svg   = inc.svg('#stage', { viewBox: [0, 0, 760, 360], title: 'Chain drive' });
const ring  = svg.part('Chainring', svg.path(inc.path.gear(N1, R1)).tone('hi'));
const cog   = svg.part('Rear cog',  svg.path(inc.path.gear(N2, R2)).tone('hi'));
const chain = svg.path(inc.path.hull([{ x: X1, y: Y, r: R1 }, { x: X2, y: Y, r: R2 }]))
                 .flow({ link: 12.7 });           // dashes sized to the pitch, moved by the engine

inc.onFrame((t, dt) => {
  ang += rpm.value * TAU / 60 * dt;
  ring.rotate(ang, X1, Y);
  cog.rotate(ang * R1 / R2, X2, Y);
  chain.flowTo(ang * R1);                          // chain travel along the path
});
```

The agent writes no createElementNS, no attribute strings, no path arithmetic for the hull or gear, and no dash maths.

### 22.6 Performance rules for SVG

- Batch writes in the frame function; never write inside an event handler (21.2).
- Do not call getBBox, getBoundingClientRect or getComputedTextLength inside the frame function. Measure once and cache.
- Move things with transform, not x and y, and do not rebuild stable path strings.
- Change state (highlight, dim, selected) by toggling a class, not by rewriting attributes on many elements.
- Dash-offset animation is cheap and is the preferred way to show flow.
- Mark decorative layers with pointer-events none.
- Pause all animation when the figure is off-screen or hidden.

### 23.2 The stage

One stage per figure. It owns the namespace, the layers, the ID prefix and the resize observer. The agent never touches createElementNS.

```js
const NS = 'http://www.w3.org/2000/svg';
let figureSeq = 0;

export function createStage(host, { viewBox, title, desc }) {
  const uid = 'f' + (++figureSeq);                 // prefix for every generated id (SV-11)
  const svg = document.createElementNS(NS, 'svg');
  svg.setAttribute('viewBox', viewBox.join(' '));  // never width/height (SV-16)
  svg.setAttribute('role', 'img');
  svg.setAttribute('preserveAspectRatio', 'xMidYMid meet');
  svg.style.cssText = 'width:100%;height:auto;display:block;touch-action:pan-y';

  const t = document.createElementNS(NS, 'title'); t.textContent = title;
  const d = document.createElementNS(NS, 'desc');  d.textContent = desc || title;
  svg.append(t, d);

  const defs = document.createElementNS(NS, 'defs');
  svg.append(defs);

  const layers = {};
  for (const name of ['back', 'mid', 'front', 'labels']) {
    const g = document.createElementNS(NS, 'g');
    g.setAttribute('data-layer', name);
    if (name === 'back' || name === 'labels') g.style.pointerEvents = 'none';
    svg.append(g); layers[name] = g;
  }

  host.append(svg);
  return { uid, svg, defs, layers, viewBox: viewBox.slice(), id: n => uid + '-' + n };
}
```

The layer order is fixed, so depth ordering is a matter of which layer a part goes in, plus the painter's sort inside the mid layer (17.3).

### 23.3 Element handles

Every element the agent creates comes back as a handle. The handle caches what it last wrote, so a frame that sets the same value costs nothing. This is where EN-11 and 22.6 are enforced in code rather than by discipline.

```js
export function handle(el) {
  const last = new Map();
  const h = {
    el,
    set(attrs) {
      for (const k in attrs) {
        const v = attrs[k];
        if (last.get(k) === v) continue;             // change-only write (SV-3)
        last.set(k, v);
        v == null ? el.removeAttribute(k) : el.setAttribute(k, v);
      }
      return h;
    },
    at(x, y)            { return h.transform(`translate(${r(x)} ${r(y)})`); },
    rotate(deg, cx = 0, cy = 0) { return h.transform(`rotate(${r(deg)} ${r(cx)} ${r(cy)})`); },
    transform(t)        { return h.set({ transform: t }); },
    tone(name)          { el.setAttribute('class', (el.getAttribute('class') || '').replace(/tone-\\S+/g, '') + ' tone-' + name); return h; },
    cls(name, on = true){ el.classList.toggle(name, on); return h; },
    show(on = true)     { return h.set({ display: on ? null : 'none' }); },
    d(path)             { return h.set({ d: path }); }
  };
  return h;
}
const r = n => Math.round(n * 100) / 100;           // shorter strings, fewer repaints
```

Rule of thumb for the agent, enforced by the paused-tweak and frame-cost checks: rebuild a d string only when a shaping parameter changed; otherwise call at, rotate or cls.

### 23.4 Path helpers

These are what stop the agent doing geometry by hand. The bicycle figure needed a gear outline and a chain hull; both are now one call.

```js
export const path = {
  // y = f(x) sampled across a range; the workhorse for graphs
  curve(fn, x0, x1, steps = 200, map = (x, y) => [x, y]) {
    let d = '';
    for (let i = 0; i <= steps; i++) {
      const x = x0 + (x1 - x0) * i / steps;
      const y = fn(x);
      if (!Number.isFinite(y)) { d += ''; continue; }   // break the line at a discontinuity
      const [px, py] = map(x, y);
      d += (d.endsWith('') && !d ? 'M' : d ? 'L' : 'M') + r(px) + ' ' + r(py);
    }
    return d;
  },

  // parametric: x(t), y(t)
  param(fx, fy, t0, t1, steps = 200) {
    let d = '';
    for (let i = 0; i <= steps; i++) {
      const t = t0 + (t1 - t0) * i / steps;
      d += (i ? 'L' : 'M') + r(fx(t)) + ' ' + r(fy(t));
    }
    return d;
  },

  // sprocket, pulley or gear outline: N teeth on pitch radius R
  gear(N, R, pitch) {
    const prof = [[R - 0.28 * pitch, -0.38], [R + 0.16 * pitch, -0.12],
                  [R + 0.16 * pitch,  0.12], [R - 0.28 * pitch,  0.38]];
    let d = '';
    for (let i = 0; i < N; i++)
      for (const [rad, k] of prof) {
        const a = (i + k) * 2 * Math.PI / N;
        d += (d ? 'L' : 'M') + r(rad * Math.cos(a)) + ' ' + r(rad * Math.sin(a));
      }
    return d + 'Z';
  },

  // belt, chain or band wrapped around two circles (outer tangent hull)
  hull(c1, c2) {
    const dx = c2.x - c1.x, dy = c2.y - c1.y, D = Math.hypot(dx, dy);
    const base = Math.atan2(dy, dx), a = Math.acos((c1.r - c2.r) / D);
    const p = (c, ang) => r(c.x + c.r * Math.cos(ang)) + ' ' + r(c.y + c.r * Math.sin(ang));
    return 'M' + p(c1, base - a) + 'L' + p(c2, base - a) +
           `A${c2.r} ${c2.r} 0 ${a > Math.PI / 2 ? 1 : 0} 1 ` + p(c2, base + a) +
           'L' + p(c1, base + a) +
           `A${c1.r} ${c1.r} 0 ${a < Math.PI / 2 ? 1 : 0} 1 ` + p(c1, base - a);
  },

  arrow(x, y, dx, dy, head = 9) {
    const a = Math.atan2(dy, dx), ex = x + dx, ey = y + dy;
    return `M${r(x)} ${r(y)}L${r(ex)} ${r(ey)}` +
           `M${r(ex)} ${r(ey)}L${r(ex - head * Math.cos(a - 0.4))} ${r(ey - head * Math.sin(a - 0.4))}` +
           `M${r(ex)} ${r(ey)}L${r(ex - head * Math.cos(a + 0.4))} ${r(ey - head * Math.sin(a + 0.4))}`;
  }
};
```

The curve helper must break the path at infinities and NaN rather than drawing a vertical spike. That is the single most common defect in generated graphs (think tan x or 1/x), so it belongs in the kit, not in agent code.

```js
export function shade(stage, name, from, to) {
  const g = document.createElementNS(NS, 'linearGradient');
  g.id = stage.id(name);                                   // f3-steel, never just 'steel'
  g.setAttribute('x1', 0); g.setAttribute('y1', 0);
  g.setAttribute('x2', 0); g.setAttribute('y2', 1);
  for (const [off, col] of [[0, from], [1, to]]) {
    const s = document.createElementNS(NS, 'stop');
    s.setAttribute('offset', off); s.setAttribute('stop-color', col);
    g.append(s);
  }
  stage.defs.append(g);
  return `url(#${g.id})`;
}
```

### 23.6 Parts: the registry that makes a figure teachable

A part is a named element the learner can point at. This one registry powers highlighting, dimming, callouts, the legend, keyboard navigation and the step walkthrough in section 24.

```js
export function createParts(stage, { onFocus }) {
  const parts = new Map();

  function part(name, h, { label = name, info = '' } = {}) {
    h.el.classList.add('part');
    h.el.setAttribute('data-part', name);
    h.el.setAttribute('tabindex', '0');                    // keyboard reachable (SV-15)
    h.el.setAttribute('role', 'button');
    h.el.setAttribute('aria-label', label);
    parts.set(name, { h, label, info });
    return h;
  }

  function highlight(name) {                               // one call, whole-figure effect
    for (const [n, p] of parts) {
      p.h.el.classList.toggle('hot', n === name);
      p.h.el.classList.toggle('dim', name != null && n !== name);
    }
    onFocus?.(name ? parts.get(name) : null);
  }

  // delegation: two listeners for the whole figure, never one per part (EN-5)
  stage.svg.addEventListener('pointerover', e => {
    const el = e.target.closest('[data-part]');
    if (el) highlight(el.dataset.part);
  });
  stage.svg.addEventListener('pointerout', e => {
    if (!e.relatedTarget?.closest?.('[data-part]')) highlight(null);
  });
  stage.svg.addEventListener('focusin', e => {
    const el = e.target.closest('[data-part]');
    if (el) highlight(el.dataset.part);
  });

  return { part, highlight, parts };
}
```

### 23.7 Pointer mapping and dragging

Converting a touch to figure coordinates is the thing agents get wrong. One helper, with a matrix cached until resize or zoom.

```js
export function createPointer(stage) {
  let inv = null;
  const refresh = () => { inv = stage.svg.getScreenCTM().inverse(); };
  new ResizeObserver(refresh).observe(stage.svg);          // measured here, never in a frame

  const toLocal = (clientX, clientY) => {
    if (!inv) refresh();
    const p = stage.svg.createSVGPoint();
    p.x = clientX; p.y = clientY;
    const q = p.matrixTransform(inv);
    return { x: q.x, y: q.y };
  };

  // draggable handle bound to a parameter (VI-4)
  function drag(h, { onMove, cursor = 'grab' }) {
    h.el.style.cursor = cursor;
    h.el.addEventListener('pointerdown', e => {
      h.el.setPointerCapture(e.pointerId);
      h.el.dataset.dragging = '1';
      e.preventDefault();
    });
    h.el.addEventListener('pointermove', e => {
      if (!h.el.dataset.dragging) return;
      onMove(toLocal(e.clientX, e.clientY));               // sets a value, marks dirty (EN-7)
    });
    const end = e => { delete h.el.dataset.dragging; h.el.releasePointerCapture?.(e.pointerId); };
    h.el.addEventListener('pointerup', end);
    h.el.addEventListener('pointercancel', end);
  }

  return { toLocal, drag, refresh };
}
```

### 23.8 Zoom and pan through the viewBox

```js
export function createView(stage, pointer) {
  const base = stage.viewBox.slice();
  let vb = base.slice(), dirty = false;
  const apply = () => stage.svg.setAttribute('viewBox', vb.map(n => Math.round(n * 10) / 10).join(' '));

  function zoomAt(factor, cx, cy) {                        // cx, cy in figure coordinates
    const k = Math.min(8, Math.max(0.5, base[2] / (vb[2] / factor))) ;
    const w = base[2] / k, h = base[3] / k;
    vb = [cx - (cx - vb[0]) * w / vb[2], cy - (cy - vb[1]) * h / vb[3], w, h];
    apply(); dirty = true;
  }

  stage.svg.addEventListener('wheel', e => {
    if (!e.ctrlKey && Math.abs(e.deltaY) < 2) return;
    e.preventDefault();                                     // non-passive: zoom is the exception
    const p = pointer.toLocal(e.clientX, e.clientY);
    zoomAt(e.deltaY < 0 ? 1.12 : 1 / 1.12, p.x, p.y);
  }, { passive: false });

  return { zoomAt, reset: () => { vb = base.slice(); apply(); pointer.refresh(); } };
}
```

Pinch is the same function driven by two pointers; keep both in view.js so the agent never writes gesture code. After any zoom, call pointer.refresh so the cached matrix is correct.

### 23.9 Flow along a path

Chains, belts, currents, blood flow, conveyor motion: all the same two lines of dash maths, which belong in the kit.

```js
export function flow(h, { link, markEvery = null, total = null }) {
  h.set({ 'stroke-dasharray': (link * 0.62) + ' ' + (link * 0.38) });
  const mark = markEvery && total
    ? handle(h.el.cloneNode()).set({ 'stroke-dasharray': (link * 0.62) + ' ' + (total - link * 0.62) })
    : null;
  if (mark) h.el.after(mark.el);
  return {
    to(distance) {                                          // one attribute write per frame
      h.set({ 'stroke-dashoffset': ((-distance % link) + link) % link });
      mark?.set({ 'stroke-dashoffset': ((-distance % total) + total) % total });
    },
    mark
  };
}
```

### 23.11 Snapshot

Snapshots back the off-screen placeholder (HO-5) and sharing. Serialise, resolve tokens to literal colours, draw to a canvas.

```js
export async function snapshot(stage, width = 760) {
  const clone = stage.svg.cloneNode(true);
  resolveTokens(clone);                                     // computed colours, no CSS vars
  const blob = new Blob([new XMLSerializer().serializeToString(clone)], { type: 'image/svg+xml' });
  const url = URL.createObjectURL(blob);
  try {
    const img = await new Promise((ok, no) => { const i = new Image(); i.onload = () => ok(i); i.onerror = no; i.src = url; });
    const c = Object.assign(document.createElement('canvas'), { width, height: width * stage.viewBox[3] / stage.viewBox[2] });
    c.getContext('2d').drawImage(img, 0, 0, c.width, c.height);
    return c.toDataURL('image/png');
  } finally { URL.revokeObjectURL(url); }
}
```

Note for the sandbox: with a strict content security policy, allow img-src data: and blob: in the shell or the snapshot silently fails.

### 23.12 Build order inside inc-svg

1. stage, handle, tone. Acceptance: a static diagram renders, themes correctly, and rewriting the same attribute values costs no DOM writes (assert with a mutation counter).
2. path. Acceptance: curve breaks at discontinuities; gear and hull reproduce the bicycle prototype exactly.
3. parts, pointer. Acceptance: hover, tap and keyboard all highlight the same part; two figures on one page do not interfere.
4. view, flow. Acceptance: pinch zoom on iPad keeps stroke weight and does not steal page scroll.
5. budget, snapshot. Acceptance: a 1,500-element figure fails the check with a message naming the count.

## 24. The teaching layer

This is the part that makes Incantly an educator rather than a renderer. A figure that merely moves is a toy. A figure teaches when it directs attention, names what changed, and invites a prediction before it reveals an answer. All of it belongs in the kit so every figure teaches the same way and the agent only supplies the content.

### 24.1 The four teaching moves

| Move | What it does | Kit call |
| --- | --- | --- |
| Direct attention | Dims everything except the part under discussion | inc.steps, parts.highlight |
| Name the change | States in words what a parameter did, not just its number | inc.explain |
| Invite a prediction | Asks before it shows, which is what makes it stick | inc.predict |
| Compare | Holds the old state beside the new one | inc.compare |

### 24.2 Steps: the guided walkthrough

The single highest-value teaching feature, and the one the bicycle figure lacks. The agent writes a list; the engine builds the stepper, the progress label, the keyboard bindings and the highlight.

```js
inc.steps([
  { say: 'Your legs turn the chainring. One pedal turn, one chainring turn.',
    focus: 'Chainring', set: { 'Rear cog teeth': 16 } },
  { say: 'The chain carries every tooth that leaves the chainring to the rear cog.',
    focus: 'Chain', hold: true },                       // hold: pause time on this step
  { say: 'The cog has fewer teeth, so it must turn further to swallow the same links.',
    focus: 'Rear cog' },
  { say: 'Fewer teeth on the back means a higher gear: more speed, harder pedalling.',
    set: { 'Rear cog teeth': 11 }, ease: 1.2 }          // ease: animate the slider over 1.2s
]);
```

Engine behaviour: next and back buttons plus arrow keys; the say text appears under the figure, never inside the drawing (22.4 rule 9); focus calls parts.highlight; set animates the parameter so the learner sees the change happen rather than jumping; hold pauses time without stopping redraws (21.1); leaving step mode restores the learner's own values.

### 24.3 Explain: words bound to the model

Numbers alone do not teach. The explain helper turns a model output into a sentence and keeps it true, because it is a function of the model (17.2), not typed text.

```js
inc.explain(() =>
  `Each pedal turn spins the wheel ${ratio().toFixed(1)} times, so the same effort ` +
  `moves you ${ratio() > 3 ? 'further but needs more force' : 'less far but turns more easily'}.`);
```

The validator rule from MD-2 still applies: literal computed numbers in strings are rejected, but a template that reads the model is fine.

### 24.4 Predict: ask before reveal

Retrieval practice is the best-evidenced thing we can add, and it costs the agent one line.

```js
inc.predict({
  ask: 'If you swap to an 11-tooth cog, does the wheel turn faster or slower per pedal stroke?',
  options: ['Faster', 'Slower', 'No change'],
  answer: 0,
  then: { set: { 'Rear cog teeth': 11 }, say: 'Fewer teeth, so the cog completes more turns per chainring turn.' }
});
```

The engine renders the question above the figure, locks the relevant slider until an answer is chosen, then runs then. Wrong answers are never scored or recorded; the point is the guess, not the mark.

### 24.5 Compare: hold the old state

```js
const ghost = inc.compare({ of: ['Rear cog teeth'], label: 'Before' });
// draws a faint duplicate of the figure at the previous value until the learner dismisses it
```

### 24.6 Pedagogical bounds

A slider that can produce nonsense teaches nonsense. Parameter ranges are part of the teaching design, so the kit supports three range kinds:

```js
inc.param('Rear cog teeth', {
  min: 11, max: 34, value: 16,                 // real-world bounds, not arbitrary
  sensible: [12, 28],                          // outside this, show a quiet note
  note: 'Below 12 teeth the chain wears very quickly on a real bike.'
});
```

The planner must justify each range in the plan (17.1), and the validator rejects a range whose extremes break the model (division by zero, negative mass, a cog with more teeth than the chainring when the figure assumes a drive ratio).

### 24.7 The text alternative

Every figure ships with a short prose description generated from the plan, shown under a toggle and read by screen readers. It is also what gets indexed, printed and pasted into a revision sheet.

```js
inc.describe(() => [
  'A chainring with ' + ring.value + ' teeth drives a cog with ' + cog.value + ' teeth.',
  'The gear ratio is ' + ratio().toFixed(2) + ' to 1.'
].join(' '));
```

| ID | Requirement | Priority |
| --- | --- | --- |
| TE-1 | inc.steps: ordered walkthrough with focus, say, set, hold, keyboard and progress | P0 |
| TE-2 | Animated parameter changes during steps rather than instant jumps | P1 |
| TE-3 | inc.explain: prose bound to the model, re-evaluated on change | P0 |

## 25. Generating in seconds

The target in 16.1 is a figure on screen within ten seconds, and something visible within one. That is an engineering problem more than a model problem.

### 25.1 Where the time goes

| Stage | Typical | Lever |
| --- | --- | --- |
| Plan call | 1 to 2 s | Small fast model, about 150 tokens out |
| Scene call | 3 to 8 s | Stream it; keep output under 80 lines by putting work in the kit |
| Validate | under 100 ms | Static scan, no execution |
| Iframe boot | 150 to 600 ms | Pre-warmed pool |
| First paint | under 100 ms | Skeleton immediately, real figure when the stream closes |

### 25.2 Paint something in the first second

The moment the plan returns, the host knows the size, the component list and the part names. That is enough to draw a skeleton: the card, the title, the control row with the right sliders disabled, and a shimmer where the drawing will be. The learner sees structure almost immediately, and the perceived wait is the scene call only.

### 25.3 Stream the fragments in order

Ask the model for HTML first, then CSS, then JS, each in its own fenced block. The host can mount the markup and styles as soon as those blocks close, so the figure appears static and then becomes live when the script arrives. Hold the script until the stream ends: partial JavaScript cannot run.

### 25.4 Pre-warm the iframe

Keep one hidden iframe already booted with the shell and engine. When a figure is ready, hand it the fragments through postMessage instead of creating a new frame, then warm a replacement in the background. This removes the boot cost from the path the learner waits on.

### 25.5 Retrieve, do not re-derive

Before generating, look up the concept in the example library by embedding similarity. On a close match, send that example as the starting point and ask only for the differences. Most school physics concepts repeat across users, so a library of a few hundred reviewed figures covers a large share of requests and cuts both latency and failure rate.

### 25.6 Cache by concept

Key a cache on a normalised concept string plus the kit version. A hit returns in well under a second with no model call at all. Figures are generic (projectile motion is projectile motion), so this is safe to share across users as long as nothing from the learner's note goes into the key.

### 25.7 Metrics to watch

Add to the dashboard in section 11: time to skeleton, time to first paint, time to interactive, cache hit rate, example-retrieval hit rate, and the share of generations needing a repair.

## 26. The 3D core, and what the reference videos actually require

Three reference videos set the quality bar. All three were reduced to one shared capability, which was then built and tested in plain SVG with no imported libraries. This section records what each video needs, the core that covers all of them, and the gaps that remain.

### 26.1 What the three references are

| Reference | What it shows | What it is made of |
| --- | --- | --- |
| A: Rubik's cube | A cube turning in 3D beside a second, abstract view of the same state (coloured dots on circular tracks), both animating together | Flat-coloured quads, depth sorted; eased face turns; two linked views of one state. A rendered video, not interactive |
| B: Euler angles (z-x-z) | An orbitable 3D axis frame with a tilting disc, coloured arcs for the three angles, three sliders and a reset | Projected axes and arcs; sampled rotations; sliders bound to one rotation matrix |
| C: Pencil sharpener | An isometric machine with a step sidebar, narration, readout chips and an idea caption | The Anatomy pattern already covered in sections 15, 17 and 24 |

### 26.2 The recommendation

**Target A's rendering with B's interaction, and keep C's teaching frame around it.** Reasons:

- A is the look we want: flat colours, no lighting, no textures. It is the cheapest high-quality style to produce and the easiest for an agent to get right.
- B proves the same drawing code becomes a teaching instrument once parameters drive the matrix. That is the Incantly product; A alone is a video.
- C is a long-session artefact (section 15.2). Its steps and readouts belong to us, its 150-part density does not.

The thing A has that our earlier figures lacked is not 3D. It is **eased transitions between discrete states**: a face turn that takes 0.45 s with an ease-in-out curve, then commits. That one addition is the difference between a demo and something that looks produced.

### 26.3 The core, proved

A working prototype renders both a turning Rubik's cube and a Euler-angle frame from one core. Measured: no imported libraries, 26 cubies, 210 quads per frame, 87 visible after culling, no console errors, correct in light and dark.

The whole core is five functions:

```js
// 1. rotation about any unit axis (Rodrigues) - the only matrix builder needed
const rotA = (a, t) => { const [x,y,z]=a, c=Math.cos(t), s=Math.sin(t), k=1-c; return [
  c+x*x*k, x*y*k-z*s, x*z*k+y*s,
  y*x*k+z*s, c+y*y*k, y*z*k-x*s,
  z*x*k-y*s, z*y*k+x*s, c+z*z*k ]; };

// 2. 3x3 multiply, 3. matrix times vector  (10 lines, omitted here)

// 4. camera: world -> camera -> screen, with weak perspective
view = v => ap(mul(rotA([1,0,0], pitch), rotA(up, yaw)), v);
proj = c => { const k = f / (f - c[2]); return [cx + c[0]*s*k, cy - c[1]*s*k]; };

// 5. visibility: a face is drawn only if its normal faces the eye
const d = [-cc[0], -cc[1], f - cc[2]];
if (nc[0]*d[0] + nc[1]*d[1] + nc[2]*d[2] <= 0) continue;
```

Everything else is per-figure content. A face turn is one line: rotate the nine cubies in the layer by `rotA(axis, dir * PI/2 * ease(t))` for rendering, then commit the rounded result to the state when `t` reaches 1.

### 26.4 Two techniques that make it fast enough

**Fixed slots instead of DOM reordering.** Painter's order normally means re-appending elements every frame, which is the slowest thing an SVG figure can do. Instead, create the polygons once, sort the face list in an array, and write face *i* into slot *i*. DOM order never changes; a frame becomes attribute writes only.

```js
faces.sort((a, b) => a.z - b.z);
for (let i = 0; i < slots.length; i++) {
  const f = faces[i];
  if (!f) { slots[i].style.display = 'none'; continue; }
  slots[i].setAttribute('points', f.pts);        // geometry changes every frame
  if (slots[i].dataset.f !== f.fill) { ... }     // colour almost never does
}
```

**Coplanar pairs need an epsilon.** A sticker drawn on top of its cubie face shares a centroid with it, so the sort is unstable and the two flicker. Push the sticker with `z + 0.02`. Any figure with a decal on a surface hits this.

### 26.5 Requirements

| ID | Requirement | Priority |
| --- | --- | --- |
| C3-1 | rotA, mul, apply: axis-angle rotation and 3x3 matrix maths | P0 |
| C3-2 | Camera with yaw, pitch, scale and weak perspective; world-to-screen in one call | P0 |
| C3-3 | Back-face culling against the eye vector, not a fixed view direction | P0 |
| C3-4 | Depth sort written into fixed element slots; no DOM reordering per frame | P0 |

### 26.6 The tween system (C3-7), which section 21 did not cover

Section 21 fixed redrawing while paused. It did not give the agent a way to move between states. This is the missing piece behind reference A.

```js
// the agent writes this
inc.tween({
  duration: 0.45,
  ease: 'inOut',
  apply: k => turnLayer(axis, layer, dir * Math.PI/2 * k),   // k goes 0 -> 1
  commit: () => cube.turn(axis, layer, dir)                  // exact state change at the end
});
```

Engine behaviour: one tween per figure at a time, the rest queued; `apply` is called every frame with the eased fraction; `commit` runs once; the dirty flag is set throughout; pausing freezes `k` without cancelling; restart clears the queue. Easing options are the same set as the timing panel in 21.4.

### 26.7 What is still missing for reference A

| Gap | Work |
| --- | --- |
| The second, abstract panel | C3-9 linked views, plus a layout helper (VI-7) so two panels share one state and one timeline |
| Narration-free pacing | A tour mode: a queue of moves played at a readable speed, which C3-8 already gives |
| Rounded sticker corners and paper texture | Styling only: stroke equal to fill with a round join is enough |

None of these need a library. The decision in section 20.3 stands: no Three.js in v1.

### 26.8 Where it goes in the plan

inc-3d (this core) is built in step 8 of section 20.2, before inc-space3d, and inc-svg (section 23) is its renderer. The tween system (C3-7) moves earlier, into step 1 with inc-core, because the control and timing layer depends on it.

## 27. The repair loop: the agent sees its own errors and fixes them

Earlier sections mention a repair attempt in single lines (HO-7, CH-3, 18.4). This section specifies it, because it is the difference between a figure that breaks in front of a learner and one that quietly fixes itself before anyone sees it.

**Principle: a generated figure is never shown to the learner until it has been run.** The scene is mounted in a hidden frame first, exercised, and only then revealed. The learner waits on the skeleton a moment longer and never sees a broken figure.

### 27.1 The pipeline

```
plan -> validate plan -> generate scene -> static validate -> PROBE RUN (hidden)
   pass -> mount for the learner
   fail -> error report -> agent repair (attempt 1) -> static validate -> PROBE RUN
            pass -> mount
            fail -> attempt 2, then 3, each only if the one before made progress
                      fail -> fallback (27.6)
```

The probe run is the in-app check suite from 17.7 and 21.5: mount, 60 frames, every parameter at minimum, middle and maximum, playing and paused, plus budget and bounds. It takes under a second, so one repair cycle costs roughly one extra scene call.

### 27.2 What gets caught, and what happens

| Kind | Caught by | Action |
| --- | --- | --- |
| Syntax or parse error | Static validate, before execution | Repair; no probe needed |
| Forbidden call (addEventListener, eval, fetch, requestAnimationFrame, network) | Static validate | Repair, naming the call |
| Hard-coded colour, fixed width or height, unknown kit function | Static validate | Repair, naming the line |
| Throw while mounting | Probe run | Repair |
| Throw inside the frame function | Probe run | Repair, with the time and parameter values that triggered it |
| NaN or Infinity reaching an attribute or a readout | Probe run, attribute guard | Repair, naming the parameter combination |
| Nothing drawn, or everything outside the stage | Probe run, bounds check | Repair |
| Slider moved while paused changes nothing (21.1) | Probe run, paused-tweak check | Repair |
| Over the element or frame-time budget | Probe run | Repair, with the measured number |
| Model output that cannot be reached from any input | Plan validate, before generation | Re-plan, not repair |
| Timeout: probe exceeds 3 s | Probe run watchdog | Treat as failure; usually an unbounded loop |

### 27.3 The error report sent back to the agent

A vague message produces a vague fix. The report must name the failure, the exact line in the agent's own fragment, and the state that caused it.

```
REPAIR 1 of 2 - the figure failed its check. Return the corrected fragments only.

FAILURE  sweep
WHEN     gravity = 1.0 (minimum), speed = 40 (maximum), t = 2.4 s, playing
ERROR    TypeError: Cannot read properties of undefined (reading 'x')
WHERE    AGENT_JS line 14, column 23
           13 | inc.onFrame((t, dt) => {
           14 |   ball.at(path[step].x, path[step].y);
           15 | });
LIKELY   step exceeds path.length when flight time is short
RULE     11. Your frame function must be safe to call with dt = 0 and at any
           parameter value inside the declared range.
```

Five things make it actionable: the failing check, the parameter values, the real error, the line with two lines of context, and the rule it broke. The LIKELY line is a hint from the error taxonomy, not a guess the agent must accept.

**Line numbers must be mapped.** The fragments are injected into the shell, so a browser stack trace points at the wrong line. Record the offset at which each fragment was inserted, or append a `//# sourceURL=agent.js` comment to the JS fragment, and translate before reporting. An unmapped line number sends the agent to fix the engine instead of its own code.

### 27.4 What the repair call sends and asks for

- **Sends:** the error report, the three fragments as they stand, the catalog line for each component used, and the rule that was broken. Not the whole conversation, not every reference file.
- **Asks for:** only the fragments that change. A JS-only fix returns JS only, which is both faster and less likely to break the markup that already worked.
- **Budget:** one automatic attempt. A second only if the first produced a genuinely different fragment; identical output means the agent has nothing more to offer and retrying burns time.
- **Guard:** a repair that fails static validation does not get a probe run. It counts as a failed attempt.

### 27.5 Errors after the figure is live

A figure can pass the probe and still throw later, because a learner edits a formula or reaches a state the sweep missed.

1. The engine catches the throw, keeps the last good frame on screen and leaves the controls alive. The figure freezes rather than disappearing.
2. A quiet line appears under it: "This figure hit a problem and is being fixed."
3. The error goes to the backend with the current parameter values and the learner's edits.
4. The repair runs in the background. On success the new scene is swapped in at the learner's current values and the line disappears.
5. On failure the line becomes "Reset to the working version", which restores the last state that passed.

A broken formula typed by the learner is not an agent failure: it shows an inline error on the formula field (FM-2) and keeps the last good result. Never send that to the agent.

### 27.6 Fallback, when repair does not work

In order of preference: the last version of this figure that passed; the nearest reviewed example for the same concept, with a note that it is a standard version; a static snapshot with the text description (TE-7) and a Retry button; and finally a plain line saying the figure could not be built, with the concept text left in the note so nothing is lost.

The learner is never shown a stack trace, a raw error, or an empty box.

### 27.7 Every failure is training data

Each repair writes a record: the concept, the plan, the fragments before and after, the error, and whether the repair worked. That log is the most valuable thing the system produces.

- A failure that recurs becomes a line in rules/core.md, or better, a kit function so it cannot happen again. The paused-slider bug in 21.1 is the model: one failure, one engine rule, one check, and the class of bug is closed.
- A repaired figure that passes and is used becomes a candidate for the example library (17.8), which cuts both latency and future failures.
- The failure taxonomy feeds the LIKELY hints in 27.3.

### 27.8 Requirements

| ID | Requirement | Priority |
| --- | --- | --- |
| RP-1 | Probe run in a hidden frame before anything is shown to the learner | P0 |
| RP-2 | Error reports carry check, parameter values, real error, mapped line with context, and the rule broken | P0 |
| RP-3 | Fragment line-number mapping from the shell back to the agent's own code | P0 |
| RP-4 | Up to three automatic repairs; another only while the one before made progress (it changed the output and did not bring back the same failures, or more of them) | P0 |
| RP-5 | Repair calls send only the report, the fragments and the relevant catalog lines | P1 |
| RP-6 | Repair returns only the fragments that change | P1 |
| RP-7 | Runtime errors after mount freeze the last good frame and repair in the background | P0 |
| RP-8 | Learner-caused formula errors are handled inline and never sent to the agent | P0 |
| RP-9 | Fallback ladder: last good version, nearest example, snapshot with description, plain message | P0 |
| RP-10 | Probe watchdog at 3 s, to catch unbounded loops | P0 |
| RP-11 | Repair log: concept, plan, before, after, error, outcome | P1 |
| RP-12 | Recurring failures become a kit function or a rule, with a check that closes the class | P1 |
| RP-13 | Dashboard metrics: first-attempt pass rate, post-repair pass rate, repair latency, top failure kinds | P1 |

### 27.9 Targets

From section 11, now with the repair loop attached: 85 percent of figures pass the probe on the first attempt, 97 percent after one repair, and a repair adds no more than 6 seconds. If post-repair pass rate sits below 95 percent, the fix is a kit function or a better example, not a fourth retry.

## 28. Films: narrated figures over time

The figure engine already has steps, a timeline, tweens, eased 3D camera moves, named parts and sound. A film strings these together under narration: 30 seconds to 4 minutes (presets 30 s, 1, 2, 3 and 4 min), played, scrubbed, touched, questioned and exported, and never a rendered file. The full plan is in [Video figures](product/video-figures.md). This section records the requirements and the rules that keep a film inside the speed budget. It extends 6.10, where video is a short clip at P2.

### 28.1 Principles

- The scene names what it wants on each beat (say this line, zoom to this part, pulse that one, cut); the engine does the timing, camera, captions and audio. Beats extend `inc.steps` (24.2), so the agent learns no second format.
- A film runs on a fixed clock in fixed steps and can seek. Seeking to t gives the frame that playing to t gives, so scrubbing, export and narration agree.
- Narration is made once, at generation time, never per viewer.
- Text is placed by a solver and checked offline at every beat; the agent gives no coordinates for captions or callouts.
- Viewers play; they do not edit.
- The generation path gains no critic or review agent. A film of one scene is one plan call and one scene call. A film of several scenes makes one scene call per scene, in parallel ([ADR 009](architecture/decisions/009-film-scene-calls.md)).

### 28.2 What changes in the engine

Today time advances by the real gap between animation frames, capped (RT-1), and nothing can go to a time. In film mode the runtime advances in fixed steps, and seeking restarts the scene and replays its steps to the target without drawing until the last one. Scene state lives in the scene's closures inside the Worker and cannot be saved, so seeking is bounded by a cap on scene length, not by checkpoints. A probe check compares seeking with playing; a scene that keeps state outside the SDK fails it and is repaired like any other failure.

### 28.3 Requirements

| ID | Requirement | Priority |
| --- | --- | --- |
| FV-1 | Film mode: scene time advances in fixed steps whatever the display frame rate | P0 |
| FV-2 | Seek to any time in a scene by replay, without drawing until the last step; scene length capped so a seek stays under the bench limit | P0 |
| FV-3 | Probe check: seeking to three times equals playing to them (readouts and part positions) | P0 |
| FV-4 | Beat fields on steps: `ease`, `cam`, `show`, `hide`, `mark`, `title`, `short`, `sfx`, `explore`, `predict`; `cut` per scene | P0 |
| FV-5 | Layout solver: captions in a band outside the drawing, callouts placed in slots that cover no part, bundled fonts measured after loading | P0 |
| FV-6 | Film checks per beat at 360, 640 and 960 px, light and dark: safe margin, caption lines, size, overlap, contrast, focus in frame, reading speed, one emphasis at a time | P0 |
| FV-7 | Player: play, pause, scrub with thumbnails, speed, volume, captions and size, transcript with seek, chapters | P0 |
| FV-8 | Offline MP4 export on the device: fixed clock, WebCodecs, faster than real time; the real-time recorder as fallback | P1 |
| FV-9 | Narration through a speech provider interface, made at generation time; beat length is audio length plus a hold; word-timed captions; beat lengths estimated from words until audio arrives | P1 |
| FV-10 | SDK-owned mixing of narration, cues and an optional bed ducked under speech; silent until the viewer turns sound on | P1 |
| FV-11 | Storyboard plan with a shared film context; one scene call per scene, in parallel, each in a normal size budget; cache and reviewed scenes first | P1 |
| FV-12 | Source map from beats to scene lines and parts; anchors by beat id, never by seconds | P1 |
| FV-13 | Questions: Answer (one small call, streamed) and Show me (beat fields on the existing scene, no new scene code) | P1 |
| FV-14 | Versions as patches over an unchanged base film; learner inserts private and pinned by anchor | P2 |
| FV-15 | Another example, Change the film, and deck mode (beats advance on click) | P2 |

### 28.4 Speed

The first scene keeps the 16.1 budget: skeleton within 1 second, playable within 10 seconds of the tap. Later scenes join as they pass their checks. The plan call cap, the scene length cap, the number of scenes per length and the whole-film deadline come from the bench, within the three-minute generation ceiling. Speech never holds back the first scene.

### 28.5 Acceptance

Films of 30 s, 1, 2, 3 and 4 minutes generated through the running Playground reach Ready with a playable first scene inside the budget, and report plan, scene, speech, check and probe times. Seeking equals playing for every reviewed scene. Every beat passes the film checks. Narration and captions stay within one frame over 4 minutes. Export matches playback frame for frame.
